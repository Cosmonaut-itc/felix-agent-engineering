## R3-A01 y comportamiento resultante

En d5, `public_projection` aplica `inputs.redact` a toda string de cualquier
objeto. `credential_values` admite valores no vacíos como `fleet-job-api@1`,
`unknown_job` y `committed`. Admitidos con origen vacío noGit, sin colisión en
contenido/rutas y enqueue-only, quedan persistidos sin ejecutar el comando.
`target` emite `unknown_job` para un selector válido inexistente antes de validar
drenado/prueba. D5 sustituye decisión en evento/recibo y api/error.code en respuesta;
con `committed` también sustituye status y decisión de una operación efectiva.
Replay y lectores perpetúan esa pérdida. El exit numérico conserva su código,
pero no repara el contrato JSON ni la auditoría. Es una deducción estática.

La regla r4 distingue **procedencia y contexto de esquema**, sin comparar contra
una lista de bytes privilegiados ni prohibir credenciales válidas:

| Contexto | Literales procedentes del protocolo que se conservan |
| --- | --- |
| Respuesta operatoria | api, operation, binding, status; contextos de error/receipt/operations/audit_events. |
| Registro paginado de operación | status y contexto de receipt. |
| Decisión, receipt o evento | action, decision, reasons tipados, reservation_before/after; contextos actor y request. |
| Petición validada | Sólo action, seleccionado por el parser entre verbos públicos. |
| Actor nativo | Sólo role, constante local-authority-owner. |
| Error | code y effects producidos por el protocolo. |

Las demás strings se redactan recursivamente con la misma primitiva
`inputs.redact`: motivo libre, operation-id y existing_operation, job/attempt/
reservation/drain/proof, target anidado, backend copiado, metadatos descriptivos
del actor (host/account/namespace/boot/birth) y todo campo no reconocido. Enteros,
booleanos, nulls, claves y formas permanecen. Una clave con nombre conocido dentro
de un objeto de datos desconocido no adquiere excepción de protocolo: el contexto
se propaga sólo por las aristas explícitas del esquema. Por ejemplo,
`request.backend="fleet-job-api@1"` se redacta y `response.api` se conserva.
`reason="unknown_job"` se redacta aunque `decision="unknown_job"` sea obligatorio.

`public_request` usa el mismo proyector con contexto request. Los tres productores
de eventos (credencial, conflicto, decisión nueva/Fault) y el receipt usan contexto
decision antes de persistir. Respuesta inmediata/replay y ambos status recorren
de nuevo la envoltura completa, incluyendo historia guardada, con declaraciones
persistidas de esa transacción o snapshot. No dependen del entorno del lector.
No se exceptúa un recibo entero ni una rama Fault; lo no reconocido se sanea.

El proyector crea objetos nuevos. `operations.request` sigue canónica cruda privada
y la comparación exacta `existing["request"] != dump(request)` permanece intacta.
La decisión recibe selectores originales; el saneamiento no concede permisos ni
altera prueba, generación, época o capacidad. Evento/receipt/binding/efecto siguen
en la misma transacción local. No se añaden campos ordinarios para resolver B-N1.

La lectura protege historia auténtica incluso cuando sus datos eran públicos al
crearla y se declararon después como credenciales. No reescribe ledger ni petición.
Un literal ya destruido por un productor anterior permanece como fue almacenado:
esta corrección no reconstruye, migra, repara ni purga esa historia. El caso escrito
posterior declara credenciales después de producir historia auténtica intacta.
